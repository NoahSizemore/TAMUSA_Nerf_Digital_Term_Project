* Noah encountered a bug when shooting at no enemies:
    * The game runs well when shooting at an NPC; however, if the player were to shoot at a wall off spawn, the game would crash.
    * The bug is in these lines of code:
    `if npc.player_distance == self.game.closest_to_player[0] and npc.alive:`
    On line *98* of `main.py`, it wipes the list at the nd of every frame. In `run()`, `check_events()` is called before it updates, so when a click is processed, the list is still empty.`single_fire_event` repopulates it at `player.py` lines 51-53 by calling `npc.ray_cast_player_npc()` on each living NPC. That only appends a distance (via distance_check, `npc.py` lines 187-204) when the ray actually reaches the NPC (i.e. it's in line of sight).
    With no enemy in line of sight, nothing is appended, the list stays [], and line 55 blows up.
    * The fix: The unguarded `closest_to_player[0]` is gone. Instead of matching NPCs by comparing floats, the shot now walks the sorted [distance, ID] list and resolves by ID, which is unique per NPC. Additionally, `distance_update()` is now being called in `player.py`. Its body is replaced with a one-line `sort(key=lambda unit: unit[0])`. The old hand-rolled insertion sort had two defects beyond being dead code: `updated_list[index + 1] = add_unit` would itself raise IndexError whenever it displaced the last element, and `unit[0]` assumed [distance, ID] pairs while distance_check was appending bare floats. On top of that, `distance_check` is now repaired. It now appends `[self.player_distance, self.ID]`, matching David's `# Distance, ID V` comment. The old version overwrote an NPC's own `player_distance` with a different NPC's value and appended nothing, which is what broke the matching.
    * Other changes made would be gaurding the ZeroDivisionError. It now uses a similar trick used in `raycasting.py`. Additionally, debug prints are removed.
